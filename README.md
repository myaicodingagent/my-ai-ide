# My AI IDE

A desktop code editor with Claude built in, for Windows. Electron + React + Monaco (the editor core of VS Code).

## Install

Run `release\My-AI-IDE-Setup-<version>.exe` (build it first, see below). The installer is unsigned, so Windows
SmartScreen shows "unknown publisher": choose *More info → Run anyway*.

On first use, click **Sign in** (status bar, or the chat panel). Your browser opens on the website; confirm the short code shown
in the app, and the app is signed in. Your plan and today's allowance appear in the status bar; click it for the account
(sign out, service address). The sign-in token is encrypted with Windows (Electron `safeStorage`) and kept only on your PC.
All model calls go through our service, which applies your plan and limits; the app never holds a model key.

**Development:** with `ANTHROPIC_API_KEY` set (or `MY_AI_IDE_DIRECT=1`) the app skips the account and talks to the provider
with that key, which is what the end-to-end tests use. `MY_AI_IDE_BACKEND_URL` points the app at another service (the default is
`DEFAULT_BACKEND_URL` in `src/main/backend.ts`: change it before building a release).

You can also open a project from a terminal: `"My AI IDE.exe" C:\code\project`.

| Search by meaning | In the search panel press **✦** and ask in plain words ("where do users log in?"). Two rankings are merged: a local word index (names are split at camelCase/snake_case), and **embeddings** from a small model (all-MiniLM-L6-v2, ~23 MB, downloaded once on first use, then fully offline; Settings → *Search by meaning on this PC* turns it off) that finds code sharing no words with the question. Claude Haiku also widens the question into likely identifiers and orders the best matches (only the question and short excerpts are sent). Vectors are cached on disk, so a project is embedded once; a large project is learned in the background and the panel says how far it got. In chat, **@codebase** attaches the matching code; the agent has a `search_codebase` tool. |
| Next edit | After you edit, Haiku predicts the change you will probably make next (the same rename on the next call site...). A box under the target lines shows it: **Tab** jumps there, **Tab** again applies, **Esc** dismisses. Off in Settings → *Next edit suggestions*. |
| Inline edit | Select code, **Ctrl+K**, describe the change, review the diff, Accept or Reject. |
| Autocomplete | Grey ghost text while you type, **Tab** accepts. Uses Claude Haiku 5.5. Toggle in the tab bar. Besides the current file it sends short excerpts of up to 3 other open files (the ones you touched most recently, or that mention the word at the caret) when you use your own key; with an account only the current file is sent for now. |
| Agent | Chat panel → **Agent**. Lists, reads and searches files; edits files and runs commands. The conversation is saved per project folder: reopen the folder and the transcript, the agent's memory of it, and the **Undo** buttons for its changes all come back (plain JSON in `%APPDATA%\my-ai-idegent`). **New** forgets it and deletes the files. |
| Background agents | **Agents** tab, or **⤴ Background** in the agent panel. A task runs on its own copy of the project (a git worktree on its own branch) while you keep working; file edits there need no approval, commands still do. When it finishes, review the changed files as diffs, then **Apply to my files** (conflicts show up like merge conflicts) or **Discard**. Your untracked files are copied into the copy and an ignored `node_modules` is linked to the original (so dependencies are there without reinstalling; do not change packages from a background task). Needs a git repository with a commit; up to 3 at a time. In an SSH folder the copy is made on the server (inside the repository's `.git/my-ai-ide-worktrees`, so `git status` does not show it) and needs `git`, `sh` and `tar` there. **Cloud agents:** in an SSH folder, tick *Keep running on the server* and the agent loop itself runs on the server, detached (`setsid`/`nohup`), so it goes on when you close the editor or the PC sleeps; the editor follows it through files in `~/.my-ai-ide/cloud/tasks/<id>` and picks it up again at the next start (reconnect to the server, then the Agents tab shows where it got to). The server needs Node.js 18+ (the runner is one file the editor copies over) and your own Anthropic API key: if the server has no `ANTHROPIC_API_KEY` of its own, the editor asks before sending yours, keeps it in a private file there and deletes it when the task ends. Commands the agent wants to run can be asked about (default), run automatically or refused. Stopping the editor does not stop a cloud agent; *Stop* on its card does. It is not a hosted service: the server is a machine you run yourself. |
| Debugger | **Run** tab. Click the margin or press **F9** for a breakpoint (give it a condition in the Breakpoints list); **F5** starts the open file, **F10** / **F11** / **Shift+F11** step, **Shift+F5** stops. Variables (expandable), watch expressions, call stack, a debug console that evaluates in the stopped frame, and a stop on uncaught exceptions. Works for **JavaScript, TypeScript** (bundled with esbuild; breakpoints and stack frames map back to your `.ts` lines through source maps), **Python** (through `debugpy`: run `pip install debugpy` once; the panel says so if it is missing) and **Go** (through Delve: palette → *Debug: Install the Go Debugger (Delve)*, or `go install github.com/go-delve/delve/cmd/dlv@latest`; the package that holds the open file is built and run). **C#**: palette → *Debug: Install the C# Debugger (netcoredbg)* downloads netcoredbg (Samsung/netcoredbg, from its GitHub releases, once, into the app's data folder; or put it on your PATH); F5 on a `.cs` file then builds the nearest `.csproj` with `dotnet build` (Debug) and runs it under the debugger, with breakpoints, stepping, variables, expressions and unhandled-exception stops. **C and C++**: palette → *Debug: Install the C/C++ Debugger* (Windows: runs `winget install MartinStorsjo.LLVM-MinGW.UCRT`, which brings clang and `lldb-dap`; Linux and macOS: install `lldb` and `clang` with your package manager) or have `lldb-dap` and `clang`/`gcc` on the PATH; F5 on a `.c`, `.cpp`, `.cc` or `.cxx` file compiles that one file with `-g -O0` (statically linked on Windows) and runs it under `lldb-dap`, with breakpoints (also in headers), stepping, variables (a `std::vector` expands), expressions and the program's output. **Java**: needs a JDK (the `javac` compiler; palette → *Debug: Install the Java Debugger (JDK)* runs `winget install EclipseAdoptium.Temurin.21.JDK` on Windows; found through `JAVA_HOME`, the PATH or the usual install folders). F5 on a `.java` file with a `main` method compiles it, and the other source files of its package that it uses, with `javac -g` and runs it under the editor's own debug adapter (built on the JDK's Java Debug Interface; it is compiled with your JDK the first time). Breakpoints (also in the other files of the program), conditions, stepping, stop on entry, uncaught-exception stops, locals and `this` with their fields, arrays, and the contents of library objects (a list shows `[1, 2, 3]`), and the Debug Console and Watch can evaluate expressions: names, fields, array elements, method calls (`list.size()`, `Math.max(a, b)`), arithmetic, comparisons, `&&`, `||`, `!` and string `+`. Palette → *Debug: Attach to Node.js Program…* connects to a Node program that is already running: give its `--inspect` port (`9229`, or `host:port`) or `pid 1234` (the process is asked to open its inspector); Stop only disconnects, the program keeps running. *Debug: Attach to Python Program…* connects to a program started with `python -m debugpy --listen 5678 script.py` (give the port or `host:port`), and *Debug: Attach to Go Process…* to a running Go program by `pid 1234` (or to a Delve server started with `dlv attach --headless --listen=:2345`, by port); all three are also in the Run menu. Choose a **launch configuration** from `launch.json` (see *Tasks and launch.json*) to set arguments, environment and folder. |

The host can also share a terminal (*Live Share: Share the Terminal…*): guests get a tab with its output, sized like the host's, and either only watch or (if the host chose so, and never in a read-only session) type in it, which runs commands on the host's PC; the host's side enforces this. *Stop Sharing the Terminal* ends it. |

| Merge editor | A conflicted file shows **Open Merge Editor** above the first conflict: Current and Incoming side by side, and the Result underneath, which you can edit. Accept Current / Incoming / Both per conflict, or all at once; **Complete Merge** writes the file and stages it. |
| Notebooks | `.ipynb` files open as notebooks (nbformat 4, so they stay compatible with Jupyter): code and text cells, run with **Shift+Enter** or ▶, Python `input()` asks in a small dialog, outputs (text, errors, images, HTML as text), execution counts, Add/Move/Delete, command mode keys (**B** below, **A** above, **D D** delete, **M**/**Y** cell type), Clear Outputs, Stop. Kernels: **JavaScript** (built in) and **Python** (your Python on PATH; no `ipykernel` needed). These two are this editor's own simple kernels (JavaScript cells have no `input()`, and Stop ends the kernel: variables are lost). **Jupyter kernels** are listed too ("Jupyter: Python 3 (ipykernel)", R, Julia... whatever is installed: found through `kernel.json` files in the usual places, `JUPYTER_PATH` and the folders of the Pythons on your PATH) and are driven with the real Jupyter messaging protocol over ZeroMQ (written into the app, nothing to install but the kernel); a notebook that names an installed kernel opens with it. With a Jupyter kernel Stop interrupts the running cell and keeps the variables, `input()` works, `clear_output()` (also with `wait=True`) and `display(..., display_id=...)` with its updates work (progress bars that redraw), and **ipywidgets** are drawn and live: sliders, buttons, boxes, `interact()` with its Output widget (the library of ipywidgets 8 draws both ipywidgets 8 and 7); their state is saved in the notebook, so they are there again after reopening it (without a kernel they only respond on screen). *File: Create New Notebook*; "{ }" or *Open as Notebook* switches between the cells and the JSON text. |
| Accessibility | Everything works from the keyboard: **F6** / **Shift+F6** move between the explorer, editor, terminal and chat, dialogs trap and restore focus, the tabs, tree, menus and pickers use the standard roles (tablist, tree, menu, combobox/listbox, dialog), and status changes (saved, search results, kernel done...) are announced to screen readers. A visible focus ring is shown for keyboard use. Every built-in theme meets WCAG AA text contrast (`npm run test:contrast` checks it, including custom themes you add). Settings: *Screen reader mode*, *Reduce motion* (your system setting is also respected). A running screen reader is detected and switches the editor and terminal into their screen reader mode by itself. The window is an *application* for the screen reader (so it leaves the keys to the editor, as VS Code does), with the conversation and welcome texts marked as documents to read with its browse mode. An open menu holds the keyboard focus and names its entry as the arrow keys move; a side bar view opened with the keyboard takes the focus; opening and saving a file is announced. |

### Agent safety

- Every file change is shown as a diff and written only after you click **Accept**. Each accepted change has an **Undo** button (kept in memory for the session).
- Every command is shown in full and runs only after you click **Run**. There is no "always allow".
- File tools cannot leave the project folder (symlinks are resolved) and cannot touch `.git`.
- Commands run in PowerShell in the project folder, stop after 60 s by default (max 10 min), and do not receive your API key.
- A run stops after 25 steps.

### Cost

With an account, usage is counted by the service against your plan (a request per question, per Apply, per commit message, five for an agent task; suggestions have their own allowance; Next edit suggestions are off by default because each one is a request). In development mode (own key) these call the Anthropic API directly and are billed to you. The agent re-sends
the conversation on every step (prompt caching is on). Autocomplete sends a request each time you pause typing; turn it off
when you do not need it. Models can be picked in each panel (Opus 5.5 default, Sonnet 5.5, Haiku 5.5).

### Publishing an update

Updates come from GitHub Releases: `electron-builder.yml` points at `myaicodingagent/my-ai-ide`. The repository must be public (a private one
would need a token inside the app). If `owner` is changed back to the placeholder `YOUR_GITHUB_USER` the app says "Updates are not set up in this build"
and makes no network calls.

For each release:

1. Raise `version` in `package.json` (for example `0.1.0` to `0.2.0`).
2. `npm run dist`. This writes `release/My-AI-IDE-Setup-<version>.exe`, its `.blockmap`, and `latest.yml`.
3. On GitHub create a release tagged `v<version>` and attach those three files (or run
   `npx electron-builder --win nsis --publish always` with a `GH_TOKEN` environment variable to upload them for you).

Installed copies with an older version then show **Update <version> available**. The download is checked against the SHA-512 in
`latest.yml` and discarded if it does not match.

To host updates yourself instead, change `publish` to `provider: generic` with a `url`, or set the environment variable
`MY_AI_IDE_UPDATE_URL` to a folder that serves `latest.yml` and the installer (this is how the tests run).

Installers are unsigned, so Windows shows the SmartScreen warning for each new version too; a code-signing certificate fixes both.

### Custom themes

Put a `.json` file in the themes folder (`%APPDATA%\my-ai-ide\themes`; Settings → **Open folder** opens it and adds a
`_example-theme.json`), then press **Reload** in Settings. Files whose name starts with `_` are ignored. You can also use
**Import…** to copy a file in, or **Duplicate current** to write the active theme out as a complete file to start from.

```json
{
  "name": "My Theme",
  "type": "dark",
  "base": "dark-modern",
  "ui": { "bg": "#1b1d2b", "side": "#161824", "accent": "#ff6ac1" },
  "syntax": { "keyword": "#ff6ac1", "string": "#5af78e", "comment": "#686868" }
}
```

- `name`: shown in the picker. `type`: `dark`, `light` or `hc` (decides the native color scheme and terminal palette).
- `base`: a built-in theme id (default: `dark-modern` / `light-modern` / `high-contrast` by type). Colors you leave out come from it.
- `ui` keys: `bg side sunken hover active border fg muted accent onAccent danger ok sel`.
  `syntax` keys: `comment keyword string number type func variable constant tag attr`.
  Colors are `#rgb` or `#rrggbb`.
- Mistakes are reported in Settings with the file name and the reason; one bad file never affects the others.

Built-in themes live in `src/renderer/src/theme.ts` in the same shape; add one to `BUILTIN_THEMES` to ship it with the app.
The tests use their own throwaway app profile (`--user-data-dir`), so they never touch your real settings or chats.

### Packaging notes

`signAndEditExecutable` is off because electron-builder's signing toolkit needs symlink rights on Windows; `build/afterPack.js`
sets the exe icon and version info with `rcedit` instead. To ship to others, get a code-signing certificate and turn it back on.

## Known limits

- Saved agent history keeps the most recent turns only (about 1.5 MB); older ones are dropped whole. The files contain file contents the agent read; they are encrypted with Windows (`safeStorage`) when it is available, and files saved by older versions are encrypted on their next save.
- Autocomplete sends the current file plus a few other open files; it does not index the rest of the project. With an account the service gets only the current file.
- Only tested on Windows 11.
- Language servers run for folders on this PC, for folders opened over SSH (there the server is started on the other computer, found on its PATH and in `~/go/bin`, `~/.cargo/bin`, `~/.local/bin`) and for folders in a WSL distribution (started inside it the same way; tested with pylsp in Ubuntu 24.04 only), use full-file sync, and a rename changes closed files through stand-in models (written to disk a moment later; undo in the editor that started the rename undoes them too, redo as well, until that file is edited again), at most 50 closed files at once.
- Extensions: the `vscode` API layer is partial (see the Extensions row). Extensions that need language clients (this editor starts language servers itself, see *Language servers*), notebooks or debug adapters do not work; other menus (`scm/change/title`, `editor/title/run`, `comments/*`, `notebook/*`, `touchBar`, `menuBar/*`...) are ignored, a tree node's icon cannot be a remote URL, a restored webview panel gets default options, and many large extensions use APIs beyond the supported set. Extension code is not sandboxed.
- The debugger handles JavaScript, TypeScript, Python (needs `debugpy`), Go (needs Delve), C# (needs the .NET SDK and netcoredbg), C/C++ (needs `lldb-dap` and a compiler) and Java (needs a JDK). C and C++ run one source file at a time (no CMake or Make projects; GDB is not supported because its debug adapter did not behave reliably in tests); Java runs one program at a time from a source file (no Maven or Gradle projects, no jar dependencies), and its expression evaluator has no lambdas, casts, `new`, generics or assignments; on Windows the MinGW toolchains from WinLibs fail to link when the user folder name contains a space, so LLVM-MinGW is what the install command uses; MSVC (`cl`) is not supported. C# needs a `.csproj` (single files without a project are not run), and the downloaded netcoredbg is not checked against a checksum (GitHub publishes none) Programs in folders opened over SSH or in a WSL distribution can be launched under the debugger for Node, Python, Go, C/C++, Java and C#, and programs already running there can be attached to while a folder there is open: the port or process id is the one on that machine (Node by port or process id, Python, Go and Java by port, C/C++ and C# by process id). Everything is compiled and run there, so the toolchain must be installed there: `node`, `python3-debugpy`, Go with `dlv`, `gcc`/`clang` with `lldb-dap`, a JDK, the .NET SDK with netcoredbg (the Linux release unpacked to `~/.local/share/my-ai-ide/netcoredbg/` or on the PATH; the editor does not download it for you there). TypeScript works in WSL folders only (the editor bundles it into the distribution's `/tmp`); over SSH debug the compiled JavaScript. All of it is tested in WSL (Ubuntu 24.04) only; over SSH the same code runs but only Node, Python and Go launch and Node attach were tested, and attaching by process id is only tested in WSL; Python and Go by process id are local only; in WSL the debugger port is carried by a `wsl.exe` bridge, tested with Ubuntu 24.04 only). Attach works for Node (port or process id), Python (debugpy port; not by process id), Go (process id or Delve port), Java (the port of a JVM started with `-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=5005`; the open folders are searched for its source files), C/C++ (process id, with `lldb-dap`; the program needs debug information) and C# (process id of a .NET program, with netcoredbg); palette → *Debug: Attach to Java Program…*, *…to C/C++ Process…*, *…to .NET Process…* (also in the Run menu); for Go, build with `-gcflags="all=-N -l"` to see variables. There is no browser debugging. Node comes from your PATH if there is one, otherwise from the app itself.
- SSH folders: files, search, a terminal, source control and the agent (see the WSL and SSH row); extensions run on this PC and see the folder through the `vscode.workspace` API only (`workspace.fs`, `findFiles`, `openTextDocument`, `workspaceFolders`; an extension that uses Node's `fs`, runs a tool on the project folder or starts a language client does not find the files; the extension is not installed on the server); language servers, the debugger and background agents need `node`/`python`+`debugpy`/`dlv` and `git`/`sh`/`tar` on the server (a server with a POSIX shell: Linux, macOS; tested against the built-in test server and against Ubuntu 24.04 with OpenSSH in Docker, not against macOS or a Windows OpenSSH server). Files over 5 MB are not opened remotely, and a lost connection is re-made when you open the folder again. Git in WSL folders runs git inside the distribution (so repositories of another user need no "trust" step, and worktrees of background agents stay readable there); a distribution without git falls back to Windows Git. Background agents in WSL folders work like the SSH ones (tested with Ubuntu 24.04).
- Search by meaning indexes up to 25,000 text files per folder. The first search in a large project is word-only while the vectors are being computed in the background; the model needs one internet download (and about 70 MB of the installer is its runtime).
- Notebooks: there is no cell-level undo across runs. Jupyter kernels: the state of the widgets in the outputs is saved in the notebook (`metadata.widgets`, as Jupyter writes it) and they are drawn again when it is reopened, but without a kernel: a slider can be moved and the new value is saved, but nothing runs until the cell is run again (a saved widget from a package that is not included is kept in the file but shown as text; widgets from extra packages such as ipympl, bqplot or ipyleaflet are not included, only the standard ipywidgets), HTML output of a cell that was run in this session runs its scripts in a frame of its own (no access to the editor; plotly, bokeh and folium output draws when the page can load what it needs from the internet), while HTML saved in a notebook that is opened again is shown without scripts until the cell is run again, `update_display_data` only changes outputs of the same cell, and a kernel that is not ipykernel cannot be interrupted on Windows (Stop ends it). Tested on Windows with ipykernel 6.28 (all of it) and 7.4 (the widget test only), and ipywidgets 7.8 and 8.1; not with IRkernel, IJulia or other kernels, and not on macOS or Linux.
- Cloud agents: only over SSH (a WSL distribution ends the processes it started, and is on this PC anyway); they use your own API key, not the account service; the model is called from the server, so it needs internet access to the API (or `ANTHROPIC_BASE_URL` set in the editor's environment is passed on); search by meaning is off there (word search only); a stopped or lost cloud task keeps its work on its branch like any other. Tested against Ubuntu 24.04 with OpenSSH in Docker and a fake model, not against the real API from a real server.
- Background agents copy untracked files up to 5 MB each (2,000 files) and only link `node_modules` when git ignores it.
- Live Share: sessions are peer to peer, with no relay server, so the host must be reachable from the guest (the same machine, the same network, a VPN, or a port forward); a session reached over "computers on my network" listens on all of the host's network cards and Windows may ask the host to allow it through the firewall. Up to 8 guests, files up to 5 MB, one session at a time (hosting or joined). Text files with Windows line endings can drift if one side types a pasted line break the other side's editor stores differently. Undo after somebody else's edit can be odd. No voice and no shared debugging. A shared terminal replays its last 200 KB of output to a guest who opens it late, so full-screen programs may look wrong until they redraw. Edits to files that a guest has not opened do not reach the guest. Tested between two instances on one PC, not across computers.
- Not built: a hosted cloud service (a cloud agent runs on a server you run yourself, see Background agents), and an audit by a person using a screen reader. Screen readers are checked by machine with NVDA (`npm run test:nvda`, see below: real key presses, and NVDA's own log of what it would say), not by a person, and not with JAWS or Narrator.
